# Круг — общий чат

«Круг» — небольшой групповой мессенджер для общения в общем чате. Проект работает как обычное Node.js-приложение без сборщика и отдельного фронтенд-фреймворка: сервер обслуживает HTTP-запросы, авторизацию, SQLite и WebSocket-соединения, а интерфейс находится в одном файле `public/index.html`.

## Возможности

- регистрация нового пользователя;
- вход по логину и паролю;
- хеширование паролей с помощью `bcrypt`;
- сохранение сессии в браузере;
- общий чат для всех зарегистрированных пользователей;
- доставка сообщений через WebSocket;
- сохранение сообщений в SQLite;
- загрузка последних 50 сообщений при подключении;
- уведомления о входе и выходе пользователей;
- список всех пользователей с состоянием «в сети» или «не в сети»;
- профиль пользователя;
- настройка компактного отображения сообщений;
- выбор эмодзи;
- копирование текста сообщения;
- удаление собственных сообщений;
- отправка по `Enter` и перенос строки по `Shift + Enter`;
- автоматическое переподключение WebSocket;
- адаптивный интерфейс для компьютеров и мобильных устройств;
- установка на телефон как PWA без отдельной сборки.

## Требования

Для запуска необходимы:

- Node.js `20.17.0` или новее;
- npm;
- свободный TCP-порт, по умолчанию `3000`.

Для установки нативных зависимостей рекомендуется использовать актуальную LTS-версию Node.js. Версии ниже `20.17.0` не поддерживаются зависимостью `sqlite3`.

## Установка

Откройте терминал в корневой папке проекта и выполните:

```bash
npm install
```

Команда устанавливает зависимости из `package.json` и использует `package-lock.json` для воспроизводимой установки.

## Запуск

Запуск в обычном режиме:

```bash
npm start
```

После запуска откройте в браузере:

```text
http://localhost:3000
```

Для установки как PWA приложение должно открываться по HTTPS (или с `localhost` для разработки). В меню браузера выберите «Установить приложение» или «Добавить на главный экран». Service worker кэширует только оболочку сайта и иконки; авторизация, API и WebSocket всегда требуют соединения с сервером.

Порт можно изменить через переменную окружения:

```bash
PORT=8080 npm start
```

В Windows PowerShell:

```powershell
$env:PORT=8080; npm start
```

При успешном запуске сервер выводит сообщение с адресом приложения. Если порт уже занят, остановите другой процесс Node.js или запустите проект на другом порту. База `database.sqlite` создается или дополняется автоматически при инициализации сервера.

Путь к базе можно изменить через `DATABASE_PATH`. Это удобно для тестов и отдельных окружений:

```bash
DATABASE_PATH=/path/to/chat.sqlite npm start
```

## Авторизация и сессии

### Регистрация

Клиент отправляет POST-запрос на `/register` с JSON-телом:

```json
{
  "login": "alex",
  "password": "secret123"
}
```

Ограничения:

- логин: от 2 до 32 символов после удаления пробелов по краям;
- пароль: от 4 до 128 символов;
- логин уникален без учета регистра.

Успешный ответ имеет статус `201`:

```json
{
  "token": "...",
  "login": "alex"
}
```

Пароль не сохраняется в открытом виде. Сервер создает bcrypt-хеш с cost-фактором `12`.

### Вход

Клиент отправляет POST-запрос на `/login`:

```json
{
  "login": "alex",
  "password": "secret123"
}
```

Успешный ответ:

```json
{
  "token": "...",
  "login": "alex"
}
```

Сессия действует 24 часа. Токен создается случайным значением длиной 32 байта и хранится на сервере в памяти процесса. Браузер сохраняет токен и имя пользователя в `localStorage` под ключом `chatSession`.

### Завершение сессии

Отдельного HTTP-метода выхода нет. Клиент удаляет сохраненную сессию, закрывает WebSocket и возвращает пользователя на экран входа. Сервер также удаляет подключение из списка активных соединений после закрытия WebSocket.

## HTTP API

### `POST /register`

Создает пользователя и возвращает новую сессию.

Коды ответа:

- `201` — пользователь создан;
- `400` — некорректные данные;
- `409` — такой логин уже существует;
- `500` — внутренняя ошибка сервера.

### `POST /login`

Проверяет логин и пароль и возвращает новую сессию.

Коды ответа:

- `200` — вход выполнен;
- `400` — не передан логин или пароль;
- `401` — неверные учетные данные;
- `500` — внутренняя ошибка сервера.

### `GET /`

Статический файл `public/index.html`, который раздается через Express.

### `GET /ws`

WebSocket endpoint для авторизованного чата. WebSocket работает на том же хосте и порту, что и HTTP-сервер. Клиент автоматически выбирает `ws://` или `wss://` в зависимости от протокола страницы.

## WebSocket-протокол

После установки соединения сервер отправляет:

```json
{
  "type": "connected"
}
```

До авторизации клиент должен отправить токен:

```json
{
  "type": "auth",
  "token": "..."
}
```

После успешной авторизации сервер отправляет историю, список пользователей и системное событие о входе.

### Клиент → сервер

#### Авторизация

```json
{
  "type": "auth",
  "token": "..."
}
```

#### Новое сообщение

```json
{
  "type": "message",
  "text": "Текст сообщения"
}
```

Сервер обрезает пробелы по краям, ограничивает текст 2000 символами и игнорирует пустые сообщения.

Для ответа к сообщению клиент дополнительно передаёт необязательное поле `replyToId` с идентификатором исходного сообщения. Сервер проверяет, что исходное сообщение существует, и сохраняет связь ответа с ним.

### Сервер → клиент

#### История

```json
{
  "type": "history",
  "messages": [
    {
      "id": 1,
      "userId": 1,
      "username": "alex",
      "text": "Привет",
      "timestamp": "2026-08-25 10:00:00"
    }
  ]
}
```

Передается не более 50 последних сообщений. В базе они выбираются от новых к старым, после чего сервер возвращает их клиенту в хронологическом порядке.

#### Новое сообщение

```json
{
  "type": "message",
  "message": {
    "id": 2,
    "userId": 1,
      "username": "alex",
      "text": "Текст",
      "timestamp": "2026-08-25 10:01:00",
      "replyToId": null,
      "replyUsername": null,
      "replyText": null
  }
}
```

Сообщение рассылается всем активным подключениям.

#### Удаление сообщения

Клиент может запросить удаление только сообщения, принадлежащего текущему пользователю:

```json
{
  "type": "delete_message",
  "messageId": 2
}
```

Сервер проверяет владельца по `session.userId`. При успешном удалении всем активным клиентам отправляется:

```json
{
  "type": "message_deleted",
  "messageId": 2
}
```

Удалить чужое сообщение нельзя. Если сообщение не найдено или принадлежит другому пользователю, сервер возвращает событие `error`.

#### Редактирование сообщения

Клиент может изменить только своё сообщение:

```json
{
  "type": "edit_message",
  "messageId": 2,
  "text": "Обновлённый текст"
}
```

Сервер проверяет владельца по `session.userId`, ограничивает текст 2000 символами и рассылает результат всем активным клиентам:

```json
{
  "type": "message_edited",
  "message": {
    "id": 2,
    "userId": 1,
    "username": "alex",
    "text": "Обновлённый текст",
    "timestamp": "2026-08-25 09:00:00"
  }
}
```

На сенсорных устройствах сообщение выбирается долгим нажатием. После выбора сверху отображаются действия для редактирования и удаления.

#### Список пользователей

```json
{
  "type": "users",
  "users": [
    {
      "id": 1,
      "login": "alex",
      "createdAt": "2026-08-25 09:00:00",
      "online": true
    }
  ]
}
```

Поле `online` вычисляется по активным WebSocket-подключениям. Оно не хранится в базе.

При выборе аватарки клиент отправляет WebSocket-событие `update_avatar` с одним из доступных эмодзи. После проверки сервер сохраняет аватарку и рассылает события `users` и `avatar_updated`.

#### Индикатор набора текста

Пока пользователь вводит сообщение, клиент временно отправляет события `typing_start` и `typing_stop`. Сервер пересылает их другим активным подключениям без записи в базу. Индикатор автоматически скрывается после отправки сообщения, потери фокуса или паузы во вводе.

#### Системное событие

```json
{
  "type": "system",
  "text": "Пользователь alex вошел в чат"
}
```

Такие события отправляются при входе и выходе пользователей. Клиент не показывает собственные события входа и выхода, но показывает события других участников.

#### Ошибки

```json
{
  "type": "error",
  "error": "Некорректный формат данных."
}
```

Если сессия отсутствует или истекла, сервер отправляет `auth_error`:

```json
{
  "type": "auth_error",
  "error": "Сессия истекла. Войдите снова."
}
```

## База данных

Проект использует SQLite-файл `database.sqlite`, расположенный в корне проекта.

### Таблица `users`

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | INTEGER | первичный ключ |
| `login` | TEXT | уникальный логин без учета регистра |
| `password_hash` | TEXT | bcrypt-хеш пароля |
| `avatar` | TEXT | выбранная аватарка-эмодзи |
| `created_at` | DATETIME | дата создания пользователя |

### Таблица `messages`

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | INTEGER | первичный ключ |
| `user_id` | INTEGER | ссылка на `users.id` |
| `text` | TEXT | текст сообщения |
| `timestamp` | DATETIME | дата и время сообщения |
| `username` | TEXT | имя автора на момент сохранения |

Для внешнего ключа включен режим `PRAGMA foreign_keys = ON`. При удалении пользователя связанные сообщения удаляются каскадно.

## Архитектура сервера

1. `server.js` создает Express-приложение.
2. Express принимает JSON-запросы и раздает каталог `public`.
3. HTTP-сервер используется одновременно как транспорт для Express и WebSocket.
4. При старте вызывается `initDB()`.
5. После инициализации базы запускается прослушивание порта.
6. HTTP-маршруты создают сессии после успешной регистрации или входа.
7. WebSocket требует токен сессии первым сообщением `auth`.
8. Авторизованное соединение добавляется в `activeConnections`.
9. При входе сервер отправляет историю и актуальный список пользователей.
10. Сообщения сохраняются в SQLite и рассылаются всем активным пользователям.

Для одного логина одновременно поддерживается одно активное WebSocket-соединение. При новом подключении старое закрывается с кодом `4001`.

## Архитектура клиента

Клиент целиком расположен в `public/index.html` и состоит из трех частей:

- HTML-разметка экранов авторизации и чата;
- CSS, включая desktop- и mobile-layout;
- JavaScript без сторонних клиентских библиотек.

Основные зоны чата:

1. левый rail быстрых разделов;
2. панель сообщений с поиском, общим чатом и аккаунтом;
3. область переписки с шапкой, историей и формой отправки.

Профиль, участники и настройки открываются в drawer-панели поверх чата. Текст сообщений и имена пользователей создаются через `textContent`, поэтому HTML из пользовательского текста не исполняется.

## Поведение переписки

- сообщения группируются по автору;
- добавляются разделители дат «Сегодня», «Вчера» и датой;
- собственные сообщения отображаются справа;
- сообщения других пользователей отображаются слева;
- прокрутка автоматически идет вниз только при нахождении пользователя около нижней границы;
- при просмотре старых сообщений текущая позиция не сбивается новым сообщением;
- у сообщения есть действие копирования текста;
- собственное сообщение можно удалить, а интерфейс сразу обновится у всех подключенных пользователей;
- WebSocket повторно подключается через 3 секунды после неожиданного закрытия.

## Безопасность и ограничения

В проекте уже предусмотрены базовые меры безопасности:

- пароли не хранятся в открытом виде;
- bcrypt используется с cost-фактором `12`;
- сообщения ограничены длиной 2000 символов;
- тело HTTP-запроса ограничено размером 10 КБ;
- SQL-запросы используют параметры вместо конкатенации пользовательского ввода;
- пользовательский текст выводится как текст, а не как HTML;
- WebSocket-соединение требует действительный серверный токен.
- WebSocket принимает только текстовые JSON-пакеты размером до 10 КБ.

Текущие ограничения, которые важно учитывать:

- сессии хранятся только в памяти процесса;
- после перезапуска сервера все ранее выданные токены становятся недействительными;
- приложение рассчитано на один серверный процесс;
- отдельного чата между двумя пользователями нет;
- нет read receipts и редактирования сообщений;
- нет загрузки файлов и изображений;
- список истории ограничен последними 50 сообщениями при подключении;
- для production-развертывания не настроены HTTPS, reverse proxy, rate limiting и централизованное хранилище сессий.

## Резервное копирование базы

Для локального проекта достаточно скопировать файл базы при остановленном сервере:

```bash
cp database.sqlite database.sqlite.backup
```

Не добавляйте резервные копии базы и другие файлы с пользовательскими данными в публичный репозиторий без необходимости.

## Production-рекомендации

Перед публикацией приложения в интернете рекомендуется:

1. включить HTTPS;
2. хранить сессии в Redis или другой общей базе;
3. вынести секреты и конфигурацию в переменные окружения;
4. добавить ограничение частоты запросов регистрации и входа;
5. добавить ограничение частоты сообщений;
6. настроить reverse proxy и корректное завершение процессов;
7. регулярно создавать резервные копии SQLite;
8. добавить журналирование и мониторинг ошибок;
9. зафиксировать поддерживаемую версию Node.js;
10. добавить автоматические тесты HTTP API и WebSocket-сценариев.
